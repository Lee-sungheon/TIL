1. 네트워크 경계와 미들웨어 — 그리고 proxy.ts로의 개명

네트워크 경계 = 브라우저와 메인 서버가 만나는 최전선(놀이공원 정문 매표소). 이 경계에서 요청을 가로채 검사하는 소프트웨어 개념이 미들웨어이고, Next 16에선 이 역할을 proxy.ts가 맡는다 (과거 middleware라는 이름을 대체).

📐 예약어 규칙 (자주 틀리는 지점)

  • 파일명은 반드시 proxy.ts/proxy.js, 함수명은 반드시 proxy — 단일 함수 export
  • 위치는 프로젝트 루트 또는 src/ 바로 아래 — app/ 안에 넣으면 절대 동작 안 함
  • pageExtensions 커스텀 시 proxy.page.ts처럼 확장자를 맞출 것
🍽️
파인다이닝의 입구 호스트 — 손님이 주방·테이블로 직행하지 못하게 입구에서 예약자 명단(인증 토큰)과 드레스코드(요청 형식)를 확인하고, 미달이면 정중히 돌려보낸다. 메인 렌더링 서버는 손님이 온 줄도 모른다.

2. 전역 프록시의 6가지 무기

export function proxy(request: NextRequest, event: NextFetchEvent) {
  const sessionToken = request.cookies.get('session_token')?.value;  // ① 쿠키 확장 API

  if (request.nextUrl.pathname.startsWith('/dashboard') && !sessionToken) {
    return NextResponse.redirect(new URL('/login', request.url));  // ② 렌더링 전 차단 — 서버 부하 0
  }

  event.waitUntil(fetch(logUrl, {...}));   // ③ 응답 먼저 보내고 백그라운드 작업은 끝까지

  const requestHeaders = new Headers(request.headers);
  requestHeaders.set('x-user-verified', 'true');              // ④ 요청 헤더 변조(검증 징표)
  const response = NextResponse.next({ request: { headers: requestHeaders } });
  response.cookies.set('last_visit', ...);                     // ⑤ 응답 쿠키 세팅
  return response;
}

export const config = {   // ⑥ matcher — 검문 범위 최적화
  matcher: [{
    source: '/((?!api|_next/static|_next/image|favicon.ico).*)',
    missing: [{ type: 'cookie', key: 'admin_session' }],   // 쿠키 없을 때만 실행
  }],
};
  • ② 라우트 보호 — 렌더링 로직 실행 전에 리다이렉트가 일어나 불필요한 서버 부하가 0. API 요청엔 Response.json(…, { status: 401 })로 화면 전환 없이 직접 응답도 가능
  • ③ event.waitUntil — 프록시는 응답 반환 시 종료되지만, 이걸로 감싼 비동기 작업(접속 로그 전송 등)은 응답을 지연시키지 않으면서 죽지 않고 완료
  • ⑥ matcher 고급 — 정규식·has(쿠키/헤더 있을 때만)·missing(없을 때만)·locale: false. 단 /_next/data는 부정 패턴으로 제외해도 강제 실행 — HTML만 막고 JSON 데이터 방어를 빼먹는 보안 누락을 프레임워크가 차단
  • 실행 순서 — next.config의 headers/redirects 처리 직후, 파일시스템·동적 라우트 평가 전
  • Node.js 런타임 기본 — 과거 Edge 제약(무거운 암호화·DB 연결 불가)에서 해방. 테스트는 next/experimental/testing/server의 unstable_doesProxyMatch(15.1+)로 유닛 테스트 가능

3. 내부 프록시 route.ts — BFF(수석 셰프)

BFF(Backend For Frontend)의 배경: 과거엔 브라우저가 여러 백엔드/MSA와 직접 통신하며 데이터 조립 부담을 떠안았다 → "프론트만을 위한 전용 백엔드를 하나 두자". Route Handler(route.ts)가 그 구현체 — 폴더가 주소를, 파일명이 실행 파일을 결정(app/api/proxy/ai-analyze/route.ts → /api/proxy/ai-analyze).

❌ 브라우저 → 외부 API 직접 호출

  • CORS 차단 — 브라우저의 SOP(동일 출처 정책) 경비병이 다른 도메인 통신을 막음. 남의 서버(OpenAI 등) CORS 설정은 우리가 못 바꿈 → 백발백중 빨간 에러
  • API 키 유출 — 키를 브라우저로 내려보내는 순간 Network 탭에서 누구나 탈취 가능

✅ 내부 프록시 경유 (3박자 사이클)

  • ① 브라우저 → 동일 도메인의 /api/proxy/… (국내 배송 — CORS 무사 통과)
  • ② route.ts가 서버에서 키를 꺼내 외부와 통신 — 서버 간 통신엔 CORS 규칙 자체가 적용되지 않는다(우회의 원리)
  • ③ 결과만 브라우저로 배달
보안의 핵심 — 환경변수 접두사 process.env.OPENAI_SECRET_KEY처럼 NEXT_PUBLIC_ 접두사가 없는 변수는 클라이언트 번들에 절대 포함되지 않고 서버에서만 읽힌다 — 브라우저는 키의 존재조차 모름. 보너스: 서버→외부 요청이므로 외부 API 쪽에 우리 서버 IP만 화이트리스트로 걸어 보안을 한 단계 더 올릴 수 있다.
👨‍🍳
수석 셰프 — 손님(브라우저)이 식자재 업체(외부 API)와 직거래하는 건 식당 규칙(CORS)상 불가. 셰프가 주방 안쪽에서 거래처와 연락하고, 셰프의 개인 연락처(API 키)는 홀의 손님에게 절대 공개되지 않는다. 손님은 요리(결과물)만 받는다.

3. 덩어리 ② — 클라이언트를 절대 믿지 마라: Zod 서버 검증

프론트 검사는 해커가 Postman으로 화면을 건너뛰고 서버에 직접 쏘면 무력하다. 실무 대원칙 = 서버에서 재검증:

export const SignupFormSchema = z.object({
  name: z.string().min(2, { message: '이름은 최소 2글자…' }).trim(),   // 공백 자동 절삭
  email: z.string().email({ message: '유효한 이메일…' }).trim(),        // RFC 표준 검증 내장
  password: z.string().min(8)
    .regex(/[a-zA-Z]/).regex(/[0-9]/).regex(/[^a-zA-Z0-9]/)          // 영문·숫자·특수문자 3중 강제
    .trim(),
});

규칙 하나라도 어기면 각 규칙에 매핑해 둔 커스텀 에러 메시지가 모여 폼 화면으로 날아간다. .trim()은 자동완성이 흘린 앞뒤 공백으로 "admin " 같은 쓰레기값이 DB에 들어가는 것을 막는다.

4. 덩어리 ③ — 서버 액션 6단계: 보안의 척추

'use server';  // 이 로직 전체를 브라우저 밖 서버 방화벽 안에 격리

export async function signup(state: FormState, formData: FormData) {
  // ① FormData → 객체 변환 후 Zod 검사 (safeParse: 실패해도 throw 없이 Result 객체)
  const validated = SignupFormSchema.safeParse(Object.fromEntries(formData.entries()));

  // ② Early Return — 안 되는 조건부터 걸러 즉시 종료 (중첩 방지 + DB 헛고생 차단)
  if (!validated.success) return { errors: validated.error.flatten().fieldErrors };

  // ③ 깨끗한 데이터 추출  ※ 실서비스라면 여기서 이메일 중복 검사 필수
  const { name, email, password } = validated.data;

  // ④ 해싱+솔트 — 원본 비밀번호는 관리자도 몰라야 한다
  const hashedPassword = await bcrypt.hash(password, 10);

  mockUsers.push({ ... });          // ⑤ 가공된 데이터만 DB 저장
  await createSession(newUserId, role, team);  // ⑥ 세션 생성 (32-2 예고)
  redirect('/dashboard');
}
  • Early Return 패턴 — 에러 조건을 문지기처럼 맨 위에 세우고 걸리면 즉시 return. 샌드위치식 중첩 대신 코드가 한눈에 읽히고, 무거운 DB 연산 전에 비정상 데이터를 차단. "어떤 로직이든 안 되는 조건부터 먼저 걸러라"
  • safeParse — 실패 시 프로그램을 멈추는 .parse()와 달리 success 플래그로 감싼 Result 객체 반환. .flatten().fieldErrors가 깊은 에러 트리를 { 필드명: [메시지…] } 1차원으로 평탄화해 UI 매핑에 최적
  • FormState 타입 — 막연한 any 대신 정확한 반환 타입 지정. TS의 장점을 극대화해 예기치 않은 에러 방지

믹서기에 간 고기 — 일반 암호화는 비밀 키로 되돌릴 수 있지만, 해싱은 단방향: 갈린 고기를 원래 덩어리로 못 되돌리듯 DB가 통째로 털려도 원본 비밀번호를 역추적할 수 없다.
  • 레인보우 테이블 공격 — 같은 1234는 같은 해시가 나오므로, 해커가 수백만 개를 미리 갈아둔 대조표로 뚫는다
  • 솔트(Salt) — bcrypt가 예측 불가능한 랜덤 텍스트를 뿌려 함께 갈아버림 → 같은 비밀번호도 매번 다른 암호문 → 대조표 무력화
  • 키 스트레칭 — bcrypt.hash(password, 10)의 10은 cost factor: 연산을 210(1,024)회 반복해 무차별 대입을 수십 년 단위로 지연
✅ 핵심 정리
· 32강 3부작: 신분증 발급(인증) → 수첩(세션) → 등급 검문(인가)
· 폼: useActionState 하나로 pending 잠금 + 서버 에러 매핑
· 검증: 클라이언트를 절대 믿지 마라 — 서버에서 Zod safeParse + Early Return
· 저장: 해싱(단방향) + 솔트(레인보우 테이블 방어) + 키 스트레칭(210) — 원본 비밀번호는 어디에도 없다
· 마무리: DB 저장 → createSession → redirect로 회원가입 사이클 완성
다음 강 예고 (32-2) 코드 마지막 줄의 createSession 내부로 — 단기 기억상실증 HTTP에서 서버가 로그인 상태를 유지하는 세션 관리의 마법(JWT·쿠키 5중 자물쇠).

32-2강. 단기 기억 상실증 극복하기

[인증 2단계] JWT 세션 관리와 쿠키의 5중 보안 자물쇠 설정

📅 2026-07-26 · 섹션 7 JWT · joseStateless 쿠키 5중 자물쇠세션 갱신/파기
🎫 HTTP는 단기 기억상실증(Stateless) — 로그인해도 다음 클릭에 "누구세요?"를 반복한다. 극복법 두 갈래: 상태 유지형(서버가 장부를 들고 영수증 번호=세션 ID만 발급 — 안전하지만 천만 유저면 장부 조회·서버 간 공유 지옥) vs 무상태형(서버는 아무것도 안 들고 JWT 자유이용권 팔찌를 브라우저에 쥐어줌 — 도장(서명)만 확인하면 되니 무한 확장). 팔찌는 쿠키에 보관 — 브라우저가 요청마다 자동 동봉. 구현은 jose로 서명(HS256)·검증하되, 핵심은 cookieStore.set의 5중 자물쇠: httpOnly(XSS), secure(스니핑), expires(시한폭탄), sameSite(CSRF), path(범위). 활동 시 expires만 갱신하는 슬라이딩 연장, 로그아웃 시 delete 한 줄로 파기. 그리고 대원칙 — JWT는 누구나 뜯어볼 수 있다, 위조만 못할 뿐: 페이로드엔 최소 식별자만.

1. 세션의 두 아키텍처 — 장부 vs 팔찌

상태 유지형 (Stateful)무상태형 (Stateless) — 현재 대세
비유서버의 거대한 장부 + 영수증 번호(세션 ID)놀이공원 자유이용권 팔찌(JWT) + 도장(서명)
요청마다장부를 매번 조회 — "1번 유저 맞네, 통과"도장만 검증 — 저장소 조회 없음
장점장부가 서버 철금고 안 — 즉시 무효화 등 통제 용이서버 자원 절약, 수평 확장(Scale-out) 자유, 속도
약점유저 천만이면 조회 부하 + 서버 증설 시 장부 공유의 복잡함발급된 토큰은 만료 전까지 서버가 강제 회수하기 어려움
🎡
"다음부터 올 땐 나한테 묻지 말고 이 팔찌만 보여줘. 내 도장이 찍혀 있으면 무조건 통과." — 서버는 팔찌를 나눠주고 내쫓은 뒤, 장부 없이 도장 진위만 확인한다. 팔찌 보관함이 쿠키: 사이트 내 이동마다 브라우저가 알아서 주머니를 털어 서버로 동봉해 주므로, 우리는 처음 한 번 넣어주기만 하면 된다.

2. session.ts — 도장 만들기, 찍기, 검사하기

import 'server-only';  // 1급 기밀 코드의 프론트 유출 시 빌드 자체를 실패시키는 잉크 폭탄
import { SignJWT, jwtVerify } from 'jose';

// ① 비밀키: openssl rand -base64 32 로 생성해 .env에 은닉 → 기계어 바이트로 번역
const encodedKey = new TextEncoder().encode(process.env.SESSION_SECRET);

// ② 발급: 알맹이(payload)를 넣어 서명 도장을 쾅
export async function encrypt(payload: SessionPayload) {
  return new SignJWT(payload)
    .setProtectedHeader({ alg: 'HS256' })   // 대칭키 해시 서명 알고리즘
    .setIssuedAt()                            // 발급 시각(iat) 스탬프
    .setExpirationTime('7d')                  // 토큰 자체 수명(exp)
    .sign(encodedKey);
}

// ③ 검증: 서명 위조·만료를 검사 — 실패 시 throw하므로 try-catch로 서버 다운 방지
export async function decrypt(session = '') {
  try {
    const { payload } = await jwtVerify(session, encodedKey, { algorithms: ['HS256'] });
    return payload;
  } catch { return null; }   // 한 글자만 조작돼도 여기로 — 즉시 폐기 처분
}

📐 페이로드 대원칙 — "위조 불가 ≠ 열람 불가"

JWT는 누구나 디코딩 사이트에 넣으면 내용물을 뜯어볼 수 있다 — 서명 덕에 위조를 못할 뿐이다(권한을 user→admin으로 한 글자만 바꿔도 서명이 깨져 폐기). 따라서 페이로드엔 유저 ID·역할 같은 최소 식별 데이터만. 비밀번호·카드번호·전화번호를 넣는 순간 사이트는 해커의 맛집이 된다.

3. 쿠키의 5중 자물쇠 — 자물쇠마다 막는 공격이 다르다

cookieStore.set('session', session, {
  httpOnly: true, secure: true, expires: expiresAt, sameSite: 'lax', path: '/',
});
자물쇠막는 공격원리
httpOnly: trueXSS (악성 스크립트의 쿠키 탈취)게시판에 심긴 악성 JS가 document.cookie로 주머니를 터는 경로를 봉쇄 — 쿠키는 HTTP 통신에서만 이동
secure: true패킷 스니핑 (공공 와이파이 도청)HTTPS(+localhost)에서만 쿠키 전송을 허용
expires방치된 세션 도용 (공용 PC)7일 뒤 브라우저가 스스로 쿠키를 소각하는 시한폭탄 — 탈취돼도 피해 시간 제한
sameSite: 'lax'CSRF (타 사이트발 위조 요청)피싱 사이트가 우리 서버로 쏘는 요청엔 쿠키를 동봉하지 않음 — 정상 최상위 이동만 허용
path: '/'—사이트 전체 경로에서 출입증이 유효하도록 범위 지정

4. 세션의 생로병사 — 슬라이딩 연장과 파기

  • updateSession (갱신) — 32-3에서 배울 전역 프록시가 페이지 이동마다 몰래 호출. 흐름: ① 쿠키에서 토큰을 꺼내 decrypt → ② 없거나 해독 실패면 Early Return → ③ 현재 시각 기준 새 7일 만료 생성 → ④ 같은 토큰을 그대로 재세팅하되 expires만 덮어쓰기. 활발한 유저는 수명이 계속 밀려나 "열심히 쓰는데 로그아웃당하는" 황당함을 방지
  • deleteSession (파기) — cookieStore.delete('session') 한 줄. 내부적으로는 Set-Cookie: Max-Age=0 만료 헤더를 내려보내 브라우저 주머니에서 흔적 없이 소각 → 세션 연결 종료
✅ 핵심 정리
· HTTP 기억상실증의 해법: Stateful(장부+영수증)에서 Stateless(JWT 팔찌+도장)로 — 확장성의 승리
· JWT: 서명(HS256)으로 위조 방지, 열람은 누구나 — 페이로드엔 최소 식별자만
· 쿠키 5중 자물쇠: httpOnly=XSS · secure=스니핑 · expires=시한폭탄 · sameSite=CSRF · path=범위 — 자물쇠마다 담당 공격이 다르다
· 수명 관리: 활동 시 슬라이딩 연장(expires 갱신), 로그아웃 시 delete 한 줄로 소각
· server-only: 기밀 코드의 프론트 유출을 빌드 단계에서 차단
다음 강 예고 (32-3) 세 번째 기둥 인가 — 전역 프록시(문지기)와 DAL(수석 셰프) 를 결합한 이중 방어망으로, 출입증 소지자가 들어갈 수 있는 방과 없는 방을 통제한다.

32-3강. 금고 앞의 이중 잠금

[인가 3단계] DAL(데이터 접근 계층)과 DTO(데이터 전송 객체)를 통한 철통 방어망

📅 2026-07-26 · 섹션 7 낙관적 vs 비관적DAL DTO3중 방어망
🏦 세 번째 기둥 인가 = "누구는 들어와도 되고 누구는 안 돼". 핵심 철학: 해커가 담장을 넘어도 금고는 못 열게 — 검사를 2단계로 쪼갠다. 1차 낙관적 인가(proxy): 모든 요청(프리패치 포함)마다 도는 대문이라 DB를 못 뒤진다 → 토큰 도장만 보고 일단 믿고 길을 연다. 2차 비관적 인가(DAL): DB 직전의 통제실 verifySession이 "토큰이 있어도 권한이 강등됐을 수 있다"는 마인드로 재검사 — React cache()로 한 요청 내 100번 호출도 연산은 1번. 마지막 3차 DTO: 흙 묻은 원본(비밀번호 해시·민감정보)에서 화면에 필요한 알맹이만 도시락 포장 — 서버가 아예 안 보내니 프론트 실수 노출이 원천 불가. Proxy → DAL → DTO 3중 방어망이 현재 웹 보안 아키텍처의 정석.

5. 공식 문서의 실무 주의 3가지 (Authentication 가이드 대조 — 전부 일치 확인)

  • ① 레이아웃 검증의 함정 — Next.js는 부분 렌더링이라 레이아웃은 페이지 이동 시 재실행되지 않을 수 있다. 상단 레이아웃에서만 검사하고 return null하는 SPA식 패턴은 공식 문서가 명시적으로 비권장("multiple entry points"라 중첩 세그먼트·서버 액션 접근을 못 막음). 검사는 데이터 소스와 가장 가까운 곳(페이지·서버 액션·DAL)에서
  • ② 서버 액션·라우트 핸들러의 독립 방어 — UI에서 버튼을 숨겨도 해커는 API 주소로 직접 쏜다. 데이터를 변경하는 모든 액션·핸들러 내부에서 verifySession을 매번 호출 (31강 팩트체크의 "Server Functions는 matcher 사각지대" 경고와 같은 결론)
  • ③ 컴포넌트 단 세밀 제어 — AdminActions처럼 권한 미달이면 null을 반환해 DOM에 그림자도 안 남기는 조건부 렌더링. 페이지 차단(굵은 제어)과 UI 요소 차단(세밀한 제어)을 함께

  • 무한 리다이렉트(ERR_TOO_MANY_REDIRECTS) — 쫓아낸 목적지(/)가 보호구역에 포함돼 있으면 "쫓아냄→검문→또 쫓아냄" 루프. protectedRoutes/publicRoutes를 겹치지 않게 분리할 것
  • server-only 누출 에러 — 'use client' 컴포넌트가 session.ts·dal.ts를 import한 것. 프레임워크가 빌드 단계에서 기밀 유출을 구출해 준 것이니 임포트 경로를 지울 것
  • bcrypt 동적 평가 에러 — bcrypt(C++ 바인딩)를 프록시에서 import한 경우. 해싱은 서버 액션(bcrypt), 프록시 토큰 검증은 jose로 역할 분리
✅ 핵심 정리 — 32강 3부작 완결
· 인가 2단계: 낙관(proxy — 도장만 보고 빠르게) + 비관(DAL — 아무도 안 믿고 꼼꼼히)
· DAL: 중앙집중 + server-only + React cache() — 지킬 곳 한곳, 비용은 요청당 1회
· DTO: 서버가 알맹이만 보낸다 — 프론트 실수가 구조적으로 불가능
· 대문에서 한 번(Proxy), 금고 앞에서 한 번 더(DAL), 금고 안에서도 필요한 것만(DTO) — 3중 방어의 철학

[UX 보안] userAgent 헬퍼를 활용한 프록시 기반 모바일 동적 리다이렉트

📅 2026-07-26 · 섹션 7 userAgentdevice.type /m 리다이렉트무한 루프 가드
📱 CSS 반응형(display: none·Tailwind md:)은 가릴 뿐, 다운로드를 막지 못한다 — 대규모 대시보드에선 모바일이 PC용 무거운 JS·데이터를 꾸역꾸역 받는 참사. 해법은 프록시에서 요청 헤더만 보고 기기를 감별해, 렌더링 서버에 닿기 전에 가벼운 모바일 전용 경로(/m/…)로 물리적으로 분기하는 것. next/server의 userAgent(req) 헬퍼가 90년대부터 내려온 통행증 문자열(User-Agent)을 파싱해 device.type('mobile'·'tablet'·… / PC는 undefined)을 발라준다. 핵심 방어 코드는 pathname.startsWith('/m') 무한 루프 가드와 정적 에셋 제외 matcher — 이 둘을 빼먹으면 각각 무한 리다이렉트와 CSS/이미지 깨짐 참사.

1. 왜 CSS 반응형만으로는 부족한가

미디어 쿼리의 치명적 한계: display: none은 화면에서 가려줄 뿐, 네트워크 다운로드 자체를 막지 못한다. PC 화면에 거대한 데이터표·분석 그래프·수많은 버튼이 렌더링되는 대시보드라면, 모바일 사용자는 안 보이는 코드를 받느라 배터리와 시간을 태운다. 단순 랜딩·블로그는 반응형으로 충분 — 물리적 분리는 "무거운 앱"의 처방이다. 과거처럼 화면이 다 그려진 뒤 프론트 JS가 "앗, 모바일이네?" 하고 버벅대는 게 아니라, 요청이 렌더링 서버에 닿기 전에 헤더만 보고 알맞은 페이지로 쏴주는 것.

2. userAgent 헬퍼 — 통행증 문자열을 발라내는 파서

브라우저는 모든 요청의 HTTP 헤더에 User-Agent라는 긴 문자열 통행증("나는 iOS 16 아이폰의 사파리야")을 실어 보낸다 — 90년대 웹 초창기부터의 유산. 과거엔 이 암호문에서 정규식으로 기종을 찾고 새 스마트폰이 나올 때마다 갱신하는 막노동이었지만, 지금은 한 줄이면 끝:

import { NextRequest, NextResponse, userAgent } from 'next/server';

const { device } = userAgent(req);   // browser·os·engine·cpu·isBot도 함께 제공
device.type의미
'mobile'스마트폰
'tablet'아이패드 등 태블릿
'smarttv' · 'console' · 'wearable' · 'embedded'TV·게임기·워치·임베디드 (문서 기준 전체 목록 — 강의는 일부만 언급)
undefined데스크톱 브라우저 — 값이 없는 게 PC라는 점 주의

3. 프록시 분기 4단계 — 그리고 2개의 필수 방어 코드

export function proxy(req: NextRequest) {
  const { device } = userAgent(req);          // ① 기기 감별
  const url = req.nextUrl.clone();            // ② 원본 수정 금지 — 복제본 조작이 기본

  if (device.type === 'mobile') {            // ③ 모바일이면
    if (url.pathname.startsWith('/m')) {      // 🛡 방어 1: 이미 /m이면 통과 — 무한 루프 차단
      return NextResponse.next();
    }
    url.pathname = `/m${url.pathname}`;      // /dashboard → /m/dashboard
    return NextResponse.redirect(url);
  }
  return NextResponse.next();                 // ④ PC·태블릿은 원래 목적지로
}

export const config = {                       // 🛡 방어 2: 정적 에셋 제외 matcher
  matcher: ['/((?!api|_next/static|_next/image|.*\\.png$).*)'],
};

💡 공식 문서의 다른 접근 — redirect 대신 rewrite

userAgent 문서의 공식 예제는 NextResponse.rewrite(url) + ?viewport=mobile 쿼리 방식이다 — URL은 그대로 두고 내부적으로만 다른 화면을 서빙. 트레이드오프: 강의의 redirect+/m 경로는 모바일 URL이 명시적(공유·분석·캐시 분리에 유리)이지만 주소가 바뀌고, rewrite는 단일 URL을 유지(같은 링크가 기기별로 다른 화면)하는 대신 어떤 화면이 나갔는지 URL만으론 알 수 없다. 서비스 성격에 따라 선택.

🚨 트러블슈팅 3종

  • "모바일 모드인데 PC 화면이 나와요" — 디바이스 툴바는 화면 크기만 바꾼다. 토글 후 반드시 F5 새로고침해야 브라우저가 모바일 User-Agent 헤더를 보내기 시작한다
  • 무한 리다이렉트(ERR_TOO_MANY_REDIRECTS) — startsWith('/m') 가드 누락 → /m/m/m/dashboard… 핑퐁. 32-3강의 protected/public 겹침 루프와 같은 계열의 실수
  • 이미지·CSS가 다 깨짐 — matcher 누락 → 프록시가 정적 파일 요청에도 /m을 붙여버림. _next/static 제외 매처는 절대 빼먹지 말 것

[요새화] next.config.ts 보안 헤더 설정으로 클릭재킹과 XSS 철벽 방어

📅 2026-07-26 · 섹션 7 보안 헤더클릭재킹 HSTSCSP
🛡️ 내부 경비(프록시·DAL·DTO)가 아무리 훌륭해도 건물 유리가 얇으면 돌 던져 깨고 들어온다 — 리액트·서버 액션 로직으로 못 막는 공격들은 HTTP 통신 밑바닥에서 일어나기 때문. 해법은 서버가 응답마다 "화면을 그릴 때 이 규칙을 지켜라"는 지시서(보안 헤더)를 내려보내는 것: X-Frame-Options(투명 iframe 클릭재킹 차단) · nosniff(.jpg 위장 스크립트의 MIME 스니핑 실행 차단) · Referrer-Policy(토큰 붙은 상세 주소 유출 절단) · HSTS(1년간 https 강제) · CSP(허락한 출처의 스크립트만 실행 — XSS 최후의 보루). 과거 Nginx·Apache의 영역이던 이 설정을 next.config.ts의 headers() 하나로 프론트 개발자가 통제한다. 섹션 7의 설계 철학으로 완결: "인증·인가는 서버 로직으로 막고, 브라우저의 빈틈은 HTTP 헤더로 감싼다."

1. 서버 로직으로 못 막는 두 가지 공격

  • 클릭재킹(Clickjacking) — "클릭을 납치한다". 해커가 "아이폰 당첨 확인!" 미끼 페이지를 만들고, 그 버튼 위에 사용자가 로그인해 둔 은행의 '송금하기' 버튼을 투명 iframe으로 정확히 겹쳐 띄운다. 당첨 버튼을 눌렀다고 생각한 클릭이 실제론 송금 버튼을 누른다
  • MIME 스니핑(MIME Sniffing) — 브라우저가 너무 똑똑한 척해서 탈. 해커가 악성 JS를 .jpg로 속여 업로드 → 브라우저가 내용을 "냄새 맡고" "어? 스크립트네? 실행해 줄게!" → XSS 완성

둘 다 브라우저가 화면을 그리기도 전, HTTP 통신 단계에서 벌어지므로 앱 코드로는 방어가 까다롭다. 33강에서 요청 헤더(User-Agent)를 읽었다면, 이번엔 반대로 응답 헤더에 보안 지시서를 실어 보내는 것.

2. next.config.ts의 5겹 방탄유리

const nextConfig: NextConfig = {
  async headers() {
    return [{
      source: '/(.*)',          // 모든 경로에 예외 없이 적용
      headers: [
        { key: 'X-Frame-Options',           value: 'DENY' },
        { key: 'X-Content-Type-Options',    value: 'nosniff' },
        { key: 'Referrer-Policy',           value: 'strict-origin-when-cross-origin' },
        { key: 'Strict-Transport-Security', value: 'max-age=31536000; includeSubDomains; preload' },
        { key: 'Content-Security-Policy',   value: "default-src 'self'; img-src 'self' https://trusted-cdn.com; script-src 'self' 'unsafe-inline';" },
      ],
    }];
  },
};
헤더막는 공격브라우저에 내리는 명령
X-Frame-Options: DENY클릭재킹"그 어떤 외부 사이트도 우리를 iframe에 넣지 마라" — 렌더링 자체를 차단
X-Content-Type-Options: nosniffMIME 스니핑 → XSS"서버가 이미지라고 했으면 이미지로만 취급 — 냄새 맡고 멋대로 실행 금지"
Referrer-Policy: strict-origin-when-cross-originURL 정보 유출외부로 나갈 땐 도메인까지만 — /reset?token=1234 같은 꼬리표는 가위로 절단
Strict-Transport-Security (HSTS)패킷 탈취"1년(31536000초)간 http를 쳐도 무조건 https로 둔갑시켜 접속"
Content-Security-Policy (CSP)XSS 최후의 보루"허락한 출처('self'·지정 CDN)의 리소스만 실행 — 심어진 코드도 실행 거부"

3. CSP — 뚫린 뒤에도 이기는 방어

해커가 모든 방어를 뚫고 게시판에 악성 코드를 심는 데 성공했더라도, CSP가 있으면 브라우저가 실행 자체를 거부한다 — "출처가 불분명한 코드는 즉시 멈추고 에러를 뿜어라". 주입 차단이 아니라 실행 차단이라는 점이 '최후의 보루'인 이유. 실무 딜레마: script-src 'self'는 인라인 스크립트를 전부 차단해 Next 개발 환경·일부 플러그인이 하얗게 멈출 수 있다 → 개발 중엔 'unsafe-inline'으로 임시 구멍, 배포 시엔 스크립트 해시(Hash)나 Nonce로 빈틈없이 메우는 게 정석.

4. 실습 — 클릭재킹을 직접 시뮬레이션하고 깨부수기

  • 공격 재현: /bank(잔액·송금 버튼) 위에 /hacker 미끼 페이지가 iframe을 겹침 — 실습에선 opacity-50으로 보이게, 실제 해커는 opacity-0
  • 방어 증거 3종: ① iframe 자리가 빈 화면으로 ② 콘솔에 "Refused to display '…/bank' in a frame because it set 'X-Frame-Options' to 'DENY'" — 승리의 로그 ③ Network 탭 Doc 응답 헤더에 5겹이 촘촘히 박힌 것 확인

🚨 트러블슈팅 — 헤더가 안 먹힐 때

  • 화면이 하얗게 멈춤 — CSP를 너무 엄격하게 건 것. 개발 환경의 인라인 스크립트가 차단됨 (위 3번의 unsafe-inline↔nonce 전략으로 해소)
  • 거부 로그가 안 뜸 — 철자 오타이거나, config 변경 후 서버 재시작을 안 한 것. next.config 수정은 반드시 dev 서버 재기동
  • ⭐ 설정 파일 충돌 (핵심) — 프로젝트에 next.config.mjs(또는 .js)가 남아 있으면 새로 만든 next.config.ts가 통째로 무시된다. 구 설정 파일을 삭제하고 하나만 남길 것 — 28강 실습 잔재가 흔한 범인

[배포 준비] 환경 변수(Environment Variables) 제어와 NEXT_PUBLIC의 보안 마법

📅 2026-07-26 · 섹션 7 NEXT_PUBLIC빌드 타임 프리징 로드 우선순위connection()
🗝️ 환경 변수 = "코드는 그대로 둔 채 실행 환경만 바꿔 끼우는 마법" — 하드코딩은 깃허브에 올라가는 순간 해커 봇의 5분 먹잇감. 핵심 멘탈 모델은 유리벽: process.env는 서버 방 안의 1급 금고라 브라우저에선 undefined(의도적 보안 설계)이고, 브라우저로 보내려면 NEXT_PUBLIC_ 접두사로 명시적 허락을 해야 한다. 단 그 방식이 빌드 시점의 텍스트 치환(인라인)이라는 게 함정의 근원 — 빌드 타임 프리징(빌드 후 .env 수정 무반응, 도커 이미지 하나로 다중 환경 배포 시 대참사)과 동적 조회 실패(process.env[varName]은 치환 대상에서 누락)가 전부 여기서 나온다. 서버 변수는 반대로 connection() 동적 렌더링이면 런타임마다 신선하게 평가. 로드 우선순위 5단계와 테스트 환경의 .env.local 무시 규칙까지 — 공식 문서를 자구까지 충실히 옮긴 강의 (통합 팩트체크 보정 0건).

1. 하드코딩의 2대 죄악

  • 보안 — const DB_PASSWORD = 'mySecret123'이 깃허브에 올라가면, 자동화 봇이 5분 만에 DB 삭제·클라우드 과금 폭탄
  • 유연성 — 로컬은 localhost DB, 운영은 AWS DB… 주소가 코드에 박혀 있으면 배포마다 코드 수정+재빌드 막노동. 환경 변수면 코드는 process.env.X라는 빈 상자만 바라보고, 노트북에선 로컬 설정이·운영에선 서버 금고가 값을 채워 넣는다

2. .env 기본기

  • 위치는 무조건 프로젝트 루트 — src/ 구조를 써도 .env는 절대 src 안에 넣지 말 것 (루트만 인식)
  • 멀티라인 지원(따옴표 안 개행 또는 \n), $ 변수 확장(URL=https://x.com/$USER — 문자 그대로의 $는 \$ 이스케이프)
  • Next 런타임 밖에서는 @next/env — Drizzle·Prisma ORM 루트 설정, 테스트 러너 셋업 등에서 loadEnvConfig(process.cwd())로 수동 강제 로드
📌 커밋 규칙 — 문서의 이중 서술 공식 문서 상단 경고는 "create-next-app 기본 템플릿은 모든 .env를 .gitignore에 등록 — 거의 커밋할 일 없다"인데, 테스트 섹션엔 ".env.test는 저장소에 포함하되 .env.test.local은 제외"가 공존한다. 실무 정리: 비밀이 든 파일은 무조건 ignore, 비밀 없는 팀 공유 기본값(특히 재현성이 생명인 .env.test)만 선택적 커밋, .env*.local은 예외 없이 ignore. 유출 사고 시엔 파일 삭제로 부족(히스토리 잔존) — 발급처에서 키 즉시 폐기(Revoke)+재발급이 유일한 정답.

3. 유리벽과 빨간펜 선생님 — NEXT_PUBLIC의 정체

서버와 브라우저 사이엔 두꺼운 유리벽이 있고 process 금고는 서버 방에만 있다 — 클라이언트 컴포넌트에서 process.env.DB_PASS는 undefined. 실수로 기밀을 렌더링하는 코드를 짜도 유출되지 않는 의도적 보안 설계다. 브라우저가 꼭 알아야 하는 공개 값(GA ID·지도 API 키)만 NEXT_PUBLIC_으로 허락하면, 빌드 시점에 "빨간펜 선생님"이 코드를 스캔해 그 자리에 실제 문자열을 타이핑해 박는다(인라인 치환):

'use client';
console.log(process.env.DB_PASS);                  // ❌ undefined — 유리벽에 막힘
console.log(process.env.NEXT_PUBLIC_ANALYTICS_ID); // ✅ 빌드 시 'abcdefg'로 텍스트 치환

const varName = 'NEXT_PUBLIC_ANALYTICS_ID';
console.log(process.env[varName]);                 // ❌ 동적 조회 — 통짜 텍스트가 아니라 치환 누락
const env = process.env;
console.log(env.NEXT_PUBLIC_ANALYTICS_ID);         // ❌ 객체 할당도 마찬가지

4. 빌드 타임 프리징 — 인라인의 대가

🧊 치명적 함정

치환은 빌드 시점에 딱 한 번 — 잉크가 마르면 끝. 빌드 후 서버의 .env를 아무리 고쳐도 클라이언트 JS는 반응하지 않는다. 도커 이미지 하나를 dev·stage·prod에 돌려 배포하면 NEXT_PUBLIC_ 값이 첫 빌드 값으로 얼어붙는 대참사(문서 원문의 경고 그대로). 런타임 동적 값이 필요하면 접두사 대신 자체 API로 클라이언트가 조회하도록 설계.

반대로 서버 전용 변수는 프리징되지 않는다 — connection()(또는 cookies() 등)으로 동적 렌더링에 진입하면 요청마다 런타임에 금고를 새로 열어 신선한 값을 평가한다:

import { connection } from 'next/server';

export default async function Component() {
  await connection();                        // 정적 생성 중단 → 동적 렌더링 모드
  const dbPassword = process.env.DB_PASS;    // 런타임마다 새로 평가
}

31강 — proxy.ts · BFF (proxy 파일 컨벤션 문서 v16.2.11 대조)

  • ① "함수명은 반드시 proxy" → 반만 맞다. 문서: "either as a default export or named proxy" — 익명 default export도 공식 지원. "단일 함수만"은 정확. 실무 결론은 강의대로 named proxy 통일이 맞되, "안 하면 동작 안 함"은 아님.
  • ② "렌더링 전 차단 → 서버 부하 0" → 과장. 절감되는 건 렌더링·데이터 페칭 비용이고, 자기호스팅에선 프록시가 바로 그 Node 서버에서 실행된다. "부하 0" 그림은 프록시가 CDN 에지에 분리 배포되는 Vercel식 구성에서만 성립.
  • ③ "Node.js 런타임 기본(default)" → 기본이 아니라 고정(only). 문서: "The runtime config option is not available… will throw an error". 타임라인: v12~15.1 Edge 전용 → 15.2 Node 실험 → 15.5 안정 → 16 Node 고정.
➕ 강의엔 없지만 문서가 경고하는 2건 ⓐ 공식 권고는 프록시를 "최후의 수단(last resort)"으로 쓰라는 것 — middleware→proxy 개명 사유 자체가 남용 억제. ⓑ Server Functions는 matcher의 사각지대 — 별도 라우트가 아니라 사용 라우트로의 POST라서 matcher가 제외한 경로의 함수 호출은 검문을 통째로 건너뛴다. 인증·인가는 각 Server Function 내부에서 항상 재검증할 것.

32-1강 — Server Actions · bcrypt

  • ④ "믹서기를 10번 반복 = 연산 강도 10배" (구술) → cost factor 10 = 210 = 1,024회 반복. 실습 자료 쪽 표기가 정확하다. cost를 1 올릴 때마다 연산량이 2배씩 는다.
  • ⑤ "전역 프록시는 엣지 런타임이라 bcrypt 비호환" → Next 16 기준 옛 서술(뿌리는 31강 ③과 동일). proxy가 Node 고정이므로 bcrypt는 기술적으로 구동 가능. 다만 "프록시 검증은 가벼운 jose, 해싱은 액션의 bcrypt"라는 역할 분리 설계 자체는 여전히 모범 사례.

32-2강 — JWT 세션 · 쿠키

  • ⑥ 슬라이딩 연장의 구멍 — updateSession은 쿠키 expires만 갱신하고 같은 토큰을 재세팅한다. 토큰 내부 exp 클레임(최초 발급 +7일)은 그대로라, 그 시점이 지나면 쿠키가 살아 있어도 jwtVerify가 만료로 거부한다. 공식 인증 가이드의 예제 코드도 동일한 구조이며, 문서는 "Check if your auth library supports refresh tokens" 팁으로 보완을 시사한다. 완전한 연장이 필요하면 갱신 시 토큰 재서명(re-sign)이 정답.
  • ⑦ "HS256 = 데이터를 마구 섞어버리는 암호화 알고리즘" (구술) → HS256(HMAC-SHA256)은 암호화가 아니라 서명이다. JWT 내용은 Base64 평문이라 누구나 열람 가능하고, 서명은 위조만 막는다(JWS, RFC 7515). 열람까지 막는 암호화는 별개 규격(JWE). 강의 스스로 "누구나 뜯어볼 수 있다"고 말한 것과 정합적인 단어는 '서명'이다. (encrypt/decrypt 함수명은 공식 가이드 예제를 따른 것이라 강의만의 잘못은 아님.)
  • ⑧ "sameSite: 'lax'는 외부에서 오는 요청에 절대 쿠키를 안 보냄" (구술) → 과장. Lax는 최상위 내비게이션 + 안전 메서드(외부 링크 클릭 GET)에는 쿠키를 동봉한다 — 그래서 메일 링크로 들어와도 로그인이 유지되는 것. 차단 대상은 크로스사이트 POST·iframe·이미지/스크립트 서브리소스다. '절대 안 보냄'은 strict의 동작이고, strict는 외부 링크 유입 시 비로그인처럼 보이는 UX 비용이 있다(실습 자료의 "최상위 탐색에서만 허용" 서술이 정확).
  • ⑨ "jose가 Next.js 15의 실무 표준 — 프록시가 엣지에서 돌아야 해서" → 근거 절반이 무효. 공식 가이드가 jose를 권장 세션 라이브러리로 소개하는 것(Edge Runtime 호환 명기, iron-session과 병기)은 사실이지만, "프록시 = 엣지" 전제는 16에서 무효(③⑤와 같은 뿌리). 웹 표준 Web Crypto 기반이라 어떤 런타임에서든 도는 jose를 쓴다는 결론 자체는 유효.

32-3강 — 인가 · DAL · DTO

  • ⑩ "최신 프록시는 Node 기본이지만, 분산 배포를 위해 엣지 런타임에서 돌리기도 한다" → 앞 강의들과 달리 "Node 기본"은 스스로 보정했으나, Next 16에선 엣지 선택지 자체가 없다 — proxy에서 runtime 설정은 에러(③ 근거와 동일). "돌리기도 한다"는 15.1 이전 이야기. jose 권장 결론은 유효. (그 외는 전부 공식 Authentication 가이드와 일치 확인 — 낙관/비관 2단계, "프리패치 요청에서도 매번 실행되니 DB 조회 금지" 서술은 문서 원문 그대로("including prefetched routes… avoid database checks"), 레이아웃 부분 렌더링 함정, return null 비권장, 서버 액션 독립 방어, DAL 중앙집중·React cache() 요청 단위 메모이제이션, DTO. 실습 proxy가 req.cookies 대신 next/headers의 cookies()를 쓰는 것도 공식 가이드의 proxy.ts 예제와 동일한 패턴이라 문제없음.)

33강 — userAgent · 기기 감지

  • ⑪ "Next 16 내부 파서가 최신 Client Hints 규격까지 알아서 해독한다" → 공식 userAgent 문서에 근거 없음 — 문서는 User-Agent 헤더 파싱만 서술하며 Sec-CH-UA-*(Client Hints) 언급이 전무하다. 실무 안심 포인트: 크롬 UA 축소(reduction) 후에도 축소된 문자열에 "Mobile" 토큰은 유지되므로 mobile/desktop 감별은 계속 유효. (그 외 정확 확인 — UA 축소·Client Hints가 표준 방향이라는 사실, device.type 값 체계와 PC=undefined, 무한 루프 가드·정적 에셋 matcher의 필요성. 덤: 공식 예제는 redirect가 아니라 rewrite+viewport 쿼리 방식.) "전 세계 에지 서버에서 실행" 반복 서술은 아래 유령 계열.

34강 — 보안 헤더

  • ⑫ "자체 운영하는 다른 도메인에서 띄워야 한다면 SAMEORIGIN으로 타협" → SAMEORIGIN은 같은 출처(same-origin)에서만 iframe을 허용한다 — 다른 도메인은 여전히 차단된다. 특정 외부 도메인을 허용하려면 CSP의 frame-ancestors 지시어에 그 도메인을 명시해야 하며(구식 X-Frame-Options: ALLOW-FROM은 폐기됨), 현대 표준에선 frame-ancestors가 X-Frame-Options의 상위 호환이다.
  • ⑬ CSP 예제의 image-src는 존재하지 않는 지시어 → 올바른 이름은 img-src. 브라우저는 미지의 지시어를 조용히 무시하므로 이미지가 default-src 'self'로 떨어져 — 허용하려던 trusted-cdn 이미지가 오히려 차단되는 조용한 버그가 된다. "오타가 에러가 아니라 다른 보안 정책이 되는" CSP의 함정. (요약 카드의 코드는 img-src로 교정해 수록.)
  • ⑭ "로컬 http에서 HSTS 헤더를 보면 브라우저가 https로 비튼다" (트러블슈팅) → RFC 6797은 비보안(http) 전송으로 받은 STS 헤더를 반드시 무시하라고 규정한다 — http://localhost 응답의 HSTS 헤더 자체는 아무 효과가 없다. 실제로 https 강제 현상이 났다면 과거 https로 접속해 HSTS가 이미 등록됐거나 브라우저의 별도 localhost 처리 등 다른 원인. "주석 처리" 처방보다 chrome://net-internals/#hsts에서 도메인 삭제가 정확한 해법.

skipTrailingSlashRedirect · skipProxyUrlNormalize — 고급 플래그 2종 심화

📅 2026-07-26 고급 플래그URL 정규화trailingSlash
Q. 31강 말미에 스치듯 언급된 skipTrailingSlashRedirect·skipMiddleware(→Proxy)UrlNormalize는 정확히 무엇을 끄는 옵션이고, 언제 쓰는가?
🎛️ 둘 다 v13.1 "Advanced Middleware flags"로 함께 도입된, Next.js가 프록시 앞단에서 자동으로 해주던 URL 손질을 끄는 스위치다. ① skipTrailingSlashRedirect = 트레일링 슬래시 자동 리다이렉트(308) 해제 — 경로별로 슬래시 정책이 다른 레거시 사이트의 점진적 마이그레이션용. ② skipProxyUrlNormalize(舊 skipMiddlewareUrlNormalize) = URL 정규화 해제 — 직접 방문(/hello)과 클라이언트 전환(/_next/data/…/hello.json)을 같은 pathname으로 보이게 하던 손질을 끄고 원본(raw) URL을 그대로 노출. 외부 프록시 연동·커스텀 fetch rewrite 같은 고급 케이스 전용이며, 켜는 순간 두 형태의 URL 분기 책임이 전부 내 코드로 넘어온다. 전용 문서 페이지는 없고 proxy 파일 컨벤션 문서의 한 섹션이 유일한 공식 서술이다.

1. skipTrailingSlashRedirect — 슬래시 리다이렉트의 주도권 회수

기본 동작부터: Next.js는 trailingSlash 설정(기본 false)에 따라 슬래시 유무를 자동 통일한다 — 기본값에선 /about/ 방문 시 /about으로 리다이렉트, trailingSlash: true면 반대. (예외: 확장자 있는 정적 파일, .well-known/ 이하 경로.) 즉 사이트 전체가 전부 아니면 전무의 한 가지 슬래시 정책을 강제받는다.

📄 문서 원문 (proxy 문서, v16.2.11)

"skipTrailingSlashRedirect disables Next.js redirects for adding or removing trailing slashes. This allows custom handling inside proxy to maintain the trailing slash for some paths but not others, which can make incremental migrations easier."

공식 예제가 용도를 정확히 보여준다 — 레거시 프리픽스(/docs, /blog)는 슬래시를 건드리지 않고 통과시키고, 나머지 경로만 프록시 안에서 수동으로 슬래시를 붙여 리다이렉트:

// next.config.js
module.exports = { skipTrailingSlashRedirect: true };

// proxy.js — 자동 리다이렉트가 꺼졌으니 정책을 직접 구현
const legacyPrefixes = ['/docs', '/blog'];

export default async function proxy(req) {
  const { pathname } = req.nextUrl;
  if (legacyPrefixes.some((p) => pathname.startsWith(p))) {
    return NextResponse.next();               // 레거시 구역: 슬래시 불문 통과
  }
  if (!pathname.endsWith('/') && !pathname.match(/파일 확장자 패턴/)) {
    return NextResponse.redirect(              // 나머지: 수동으로 슬래시 부착
      new URL(`${pathname}/`, req.nextUrl));
  }
}
⚠️ 대가 이 플래그를 켜는 순간 모든 경로의 슬래시 정책 책임이 프록시 코드로 이관된다. 처리를 빼먹은 경로는 /about과 /about/이 둘 다 200으로 공존 — 검색엔진엔 중복 콘텐츠(SEO 감점 요인)가 된다. canonical 태그·리다이렉트 커버리지를 스스로 보장해야 하는, 말 그대로 마이그레이션 전용 도구.

2. skipProxyUrlNormalize — "정규화"가 뭔지부터

Pages Router에서 클라이언트 사이드 전환은 HTML이 아니라 GET /_next/data/{buildId}/hello.json 형태의 데이터 요청으로 온다(App Router의 RSC 요청도 유사). Next.js는 프록시가 이 요청을 받기 전에 pathname을 /hello로 정규화해서 넘긴다 — 직접 방문이든 클라이언트 전환이든 프록시 눈에는 같은 경로로 보이게 하는 손질이다:

// GET /_next/data/build-id/hello.json 수신 시 proxy 안에서
console.log(req.nextUrl.pathname);
// 기본(정규화 ON):  '/hello'          ← 직접 방문과 동일하게 보임
// 플래그 ON(스킵):  '/_next/data/build-id/hello.json'  ← 원본 그대로

🔗 31강 "_next/data 강제 실행"과 한 세트다

31강에서 본 "_next/data는 부정 매처로 제외해도 강제 실행"(빠져나갈 수 없게)과 이 정규화(같은 경로로 보이게)는 같은 보안 설계의 양면이다. 덕분에 pathname.startsWith('/dashboard') 한 줄이 HTML 방문과 JSON 데이터 요청 모두에 동일하게 걸린다 — 페이지는 막았는데 데이터 라우트는 뚫리는 구멍을 프레임워크 차원에서 봉쇄. skipProxyUrlNormalize는 바로 이 안전장치의 한 축을 끄는 것이다.

그럼 언제 끄나? 문서가 드는 케이스는 두 가지 — ① 원본 URL을 그대로 넘겨야 하는 외부 프록시 연동 등 "full control by using the original URL"이 필요한 고급 케이스, ② (v16 문서 추가분) NextResponse.rewrite() 대신 커스텀 fetch()로 rewrite를 구현할 때 — RSC 요청의 내부 Flight 헤더·URL 형태가 필요한데 정규화가 이를 가려버리므로 이 플래그로 원형을 수신한다. 켜면 프록시 로직이 /hello와 /_next/data/…/hello.json 두 형태를 직접 분기해야 하며, 놓치면 매처·인증 로직에 구멍이 난다.

3. 이름과 문서 위치 — 확인된 사실

  • 도입: 둘 다 Next.js 13.1의 "Advanced Middleware flags"로 동시 도입. proxy 문서 원문: "In v13.1 of Next.js two additional flags were introduced for proxy, skipProxyUrlNormalize (formerly skipMiddlewareUrlNormalize) and skipTrailingSlashRedirect" — 개명 사실이 문서에 명시돼 있다. skipTrailingSlashRedirect는 이름에 middleware가 없어 그대로 유지.
  • 전용 config 문서 페이지는 없다 — next-config-js/skipTrailingSlashRedirect·…/skipProxyUrlNormalize URL은 404(직접 확인). 공식 서술은 proxy 파일 컨벤션 문서의 "Advanced Proxy flags" 섹션이 유일.
  • 우리 프로젝트: lessee·lessor 모두 trailingSlash 기본값 + 정규화 기본값으로 충분 — 슬래시 정책이 갈리는 레거시 경로도, 커스텀 fetch rewrite도 없다. lessee의 stay middleware는 오히려 정규화 덕분에 pathname 분기가 단순해지는 수혜자다. 둘 다 켤 이유 없음.

📁 /api/proxy는 프레임워크 요구사항이 아니라 강사의 폴더 정리 컨벤션이다. proxy 서브폴더는 없어도 되고, App Router에선 /api 프리픽스조차 필수가 아니다 — route.ts는 app/ 어디에나 중첩 가능("nested anywhere"), 공식 문서 예제부터 app/posts/route.ts·app/rss.xml/route.ts처럼 /api 없는 경로를 쓴다. 유일한 하드 규칙은 같은 세그먼트에 page와 route 공존 불가 — /api 관례가 널리 쓰이는 실질 이유가 바로 이 충돌의 구조적 회피다. 단 Pages Router(우리)는 다르다: pages/api/만큼은 진짜 예약 경로.

  • 일괄 매칭 — 외부 중계 전용 라우트를 /api/proxy/… 한 프리픽스로 모아두면 proxy.ts의 matcher('/api/proxy/:path*'), 로깅, CDN 캐시 규칙에서 한 줄로 잡을 수 있다. 조직적 이점이지 동작 요건은 아니다.
  • ⚠️ 명칭 겹침 주의 — Next 16에서 proxy가 예약 파일명(루트의 proxy.ts)이 된 마당에 폴더명까지 proxy면 용어 혼동의 소지가 있다. 폴더명 자체엔 예약 의미가 없어 동작엔 지장 없지만, 새로 짓는다면 app/api/external/ 같은 이름이 더 명확하다.

bcrypt.compare(입력값, 저장된해시)의 내부 3단계: ① 저장된 60자에서 cost와 솔트를 파싱 → ② 방금 입력된 비밀번호를 그 동일한 솔트+cost로 재해싱 → ③ 결과가 저장된 해시 부분과 일치하는지 비교. 검증 시엔 새 솔트를 뽑지 않으므로 "같은 입력 + 같은 솔트 = 항상 같은 출력"이라는 해시의 결정적 성질이 그대로 성립한다.

솔트가 공개돼도 되는 이유 — 목적이 비밀 유지가 아니라서다: 레인보우 테이블 무력화(유저마다 다른 솔트 → 대조표를 유저당 새로 만들어야 함) + 동일 비밀번호 은폐(같은 1234도 DB엔 전혀 다른 문자열 → "이 두 계정 비밀번호가 같다"는 정보조차 유출 안 됨).

2. bcrypt엔 비밀키가 없다 — 케르크호프스 원칙의 극단

3. 뉘앙스 — 해싱은 서버에서 일어난다

사용자의 123은 평문 그대로 HTTPS 터널을 타고 서버에 도착하고, 서버가 솔트를 꺼내 해싱·비교한다. 클라이언트가 미리 해싱해 보내면 오히려 그 해시값 자체가 사실상 비밀번호가 돼(탈취 시 그대로 로그인 가능) 보안상 무의미해진다. 역할 분담: 전송 구간 보호 = HTTPS, 저장 보호 = 해싱.

4. 함정 — "역추적 불가"와 "알아낼 수 없다"는 다르다

역함수는 없지만 해커에겐 우회로가 있다: 자기도 똑같이 대입해보는 것. 훔친 해시에서 솔트를 꺼내 123, 1234, password… 후보를 순서대로 해싱하며 일치를 찾는다 — 서버의 검증 절차를 오프라인에서 무한 반복하는 것뿐이라 막을 수 없다.

  • 비밀번호가 123이면 → 모든 사전 공격 목록의 최상단 후보라 DB 유출 시 사실상 몇 초 안에 뚫린다
  • 키 스트레칭(cost 10 = 210회)의 역할은 시도 한 번의 단가를 1,024배로 올리는 것이지 시도 자체를 막는 게 아니다
  • 후보 공간이 천문학적인 강한 비밀번호여야 "수십 년" 방어가 실제로 성립

httpOnly 전환 설계 — JS 쿠키 접근의 대체 패턴과 우리의 선택

📅 2026-07-26 httpOnly힌트 쿠키Bearer→쿠키 인증zaritalk 실측
Q. httpOnly는 JS의 쿠키 접근을 막는데, zaritalk-front는 쿠키를 까서 쓰는 데가 많다 — 대표적으로 로그인 유무 판단과 AB 테스트 pk 추출. httpOnly를 적용한다면 어떻게 대체하나?
🔐 실측해 보니 두 사례는 한 뿌리다 — 쿠키를 읽는 게 아니라 쿠키에 담긴 JWT 토큰 자체를 클라이언트에서 까보는 구조("JWT는 누구나 열람 가능"의 정당한 활용). 해법의 원리는 자격(토큰)과 파생 정보(로그인 여부·PK·role)의 분리: 자격은 httpOnly 금고에, 파생 정보는 열람 가능한 별도 채널로. 대체 패턴은 ① /api/me 세션 조회 ② 힌트 쿠키(이중 쿠키) ③ SSR 주입 세 가지이며, 진짜 걸림돌은 클라이언트가 토큰을 읽어 Bearer 헤더를 직접 조립하는 아키텍처다. 우리 방향(결정): ② 힌트 쿠키 + ⓑ API 서버 쿠키 인증 직접 수용 — 단기에 토큰 까는 코드를 걷어내고, 장기적으로 Bearer 조립 자체를 없앤다.

1. 현재 구조 진단 — 두 사례는 같은 토큰을 깐다

  • 로그인 유무 + API 인증 — checkAuthToken(libs/api/src/utils/apiFetcher/auth.ts)이 js-cookie로 토큰 쿠키를 읽어 존재 여부로 로그인을 판단하고(없으면 /logout 리다이렉트), 있으면 Authorization: Bearer 헤더를 클라이언트에서 직접 조립해 별도 도메인 API를 호출. SSR 분기는 req.cookies로 동일 작업
  • AB 테스트 pk — HackleProvider(libs/hackle/src/context/index.tsx)가 같은 토큰 쿠키를 useCookieState로 구독하고, parseJWT(libs/shared/utils/src/lib/session.ts)가 atob으로 페이로드를 열어 PK·role 추출 → hackleClient.setUserId(`${env}-${role}-${PK}`)

2. 원리 — 자격과 파생 정보를 분리한다

httpOnly로 잠가야 하는 건 자격 증명(토큰) 하나뿐이다. 클라이언트 JS가 실제로 필요로 했던 건 토큰이 아니라 거기서 파생된 비민감 정보(로그인 여부·PK·role)다. 이 둘을 분리하면 파생 정보는 위조돼봤자 UI가 잠깐 속을 뿐 — 실제 권한은 항상 서버가 httpOnly 토큰으로 재검증한다. Next.js 공식 인증 가이드의 "낙관적(optimistic) 체크 vs 보안 체크" 구분과 같은 프레임.

3. 대체 패턴 3가지

패턴동작특징
① /api/me 세션 조회브라우저 fetch에 httpOnly 쿠키가 자동 동봉(JS가 못 읽을 뿐, 동일 도메인 요청엔 브라우저가 실어줌) → BFF가 서버에서 열어 { isLoggedIn, pk, role } 반환, React Query 캐싱가장 정석. 초기 렌더에 요청 1회 추가
② 힌트 쿠키 (이중 쿠키)로그인 시 서버가 쿠키 2개 발급: httpOnly 실토큰 + non-httpOnly member_hint(pk·role 등 비민감 파생 정보만)클라 코드 변경 최소 — getCookieItem이 읽는 대상만 힌트로 교체. Hackle 식별도 힌트만으로 충분
③ SSR 주입getServerSideProps의 req.cookies는 httpOnly 쿠키도 읽는다(차단 대상은 브라우저 JS뿐) → 서버에서 파싱해 props로 전달현 checkAuthToken 서버 분기의 자연스러운 확장

4. 진짜 걸림돌 — Bearer 헤더 아키텍처

토큰이 httpOnly가 되면 클라이언트의 Authorization: Bearer 조립 자체가 불가능해진다. 우회로는 둘: ⓐ API 호출을 동일 도메인 BFF(rewrite·pages/api)로 우회시켜 서버가 헤더를 붙이거나, ⓑ API 서버가 쿠키 인증을 직접 수용하도록 전환. 어느 쪽이든 전체 fetch 경로와 앱 웹뷰의 토큰 주입 연동(appProtocol 계열)에 영향이 가는 공사다.

✅ 우리 방향 (결정, 2026-07-26) — ② 힌트 쿠키 + ⓑ 쿠키 인증 직접 수용

  • 단기 (②) — 로그인 응답에 힌트 쿠키를 추가 발급하고, 토큰을 클라에서 까는 코드부터 걷어낸다: HackleProvider·로그인 판단이 토큰 원본 대신 member_hint를 보게. 이것만으로 "XSS 발생 시 토큰 즉시 탈취"라는 최악 시나리오의 노출 면적 축소 준비 완료
  • 장기 (ⓑ) — API 서버가 httpOnly 쿠키를 직접 인증 수단으로 수용 → 클라이언트의 Bearer 조립 코드가 통째로 사라진다. BFF 중계(ⓐ) 대비 홉 추가·서버 부하 없이 아키텍처가 단순해지는 장점
  • ⓑ의 체크리스트 — ⑴ 쿠키 도메인 정렬: API가 별도 서브도메인이면 Domain=.zaritalk.com 공유 쿠키 필요 ⑵ CORS: Access-Control-Allow-Credentials: true + 와일드카드 불가·구체 Origin 명시, fetch엔 credentials: 'include' ⑶ CSRF 재점검: Bearer 헤더는 브라우저가 자동으로 안 붙여서 CSRF에 면역이었지만, 쿠키 인증은 자동 동봉이라 sameSite+CSRF 토큰 방어가 필수로 승격 ⑷ 앱 웹뷰의 토큰 주입 연동 변경

Q. zaritalk-front가 쓰는 next.config의 env: 키는 어떻게 동작하고, 35강의 .env 방식과 어떤 차이가 있나?

1. 동작 원리 — DefinePlugin 텍스트 치환

빌드 시 webpack DefinePlugin(Turbopack도 동등 기능)이 코드의 process.env.customKey라는 통짜 텍스트를 찾아 실제 문자열로 갈아끼운다 — 문서 예시 그대로 {process.env.customKey} → {'my-value'}. 여기서 두 가지 제약이 파생된다:

  • 구조 분해 불가 — const { customKey } = process.env는 실패(문서 명시). 35강의 "동적 조회 실패"와 같은 뿌리 — 치환기는 통짜 텍스트만 찾는다
  • 서버 번들에도 동결 — 치환이 서버·클라 컴파일 양쪽에 적용되므로, .env의 접두사 없는 변수와 달리 connection() 동적 렌더링을 해도 런타임 재평가가 안 된다. 빌드 시점 값으로 양쪽 다 하드코딩

2. 발견 상세

  • ① seo-lessor-community가 최대 구멍 — prod 빌드 워크플로가 존재하는 공개 SEO 서비스인데 보안 헤더가 한 장도 없다. 다른 앱의 헤더 블록을 복사하면 되는 최저 비용·최우선 개선.
  • ② CSP 전 앱 부재 — 34강의 "최후의 보루"가 없다. Hackle·Clarity·Adrop·채널톡 등 서드파티가 많아 일괄 강제 시 화면 백지화(34강 트러블슈팅 그대로) 위험 → Content-Security-Policy-Report-Only로 위반 리포트만 수집하며 허용 목록을 다듬는 단계적 도입이 정석.
  • ③ SAMEORIGIN은 적절한 선택 — 통합 팩트체크 ⑫에서 확인했듯 같은 출처만 iframe 허용. 앱 웹뷰는 iframe이 아니라 무관하고, DENY보다 유연해 우리 상황에 맞다.
  • ④ 미세 강화 여지 2건 — ⓐ Referrer-Policy를 현대 기본값 strict-origin-when-cross-origin으로 올리면 HTTPS→HTTP 다운그레이드 시 origin조차 안 보냄. ⓑ poweredByHeader: false 미설정 — X-Powered-By: Next.js 노출(핑거프린팅, 심각도 낮음).
  • ⑤ 참고 관찰 (32강 연계) — next.config의 env: 키는 NEXT_PUBLIC_ 접두사와 무관하게 전부 클라이언트 번들에 인라인된다. HACKLE_SDK_KEY(공개용)는 무해하지만, lessee의 BOMULSEOM_BASIC_TOKEN/SIGN_KEY 하드코딩 자격증명도 함께 노출된다 — 클라이언트 사용 설계라면 의도된 노출이나, "env는 서버 전용"이라는 32강 명제가 env: 키에는 적용되지 않는다는 점을 기억할 것.
