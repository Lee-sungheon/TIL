25강. 속도의 신세계

[빌드&캐시] Turbopack의 점진적 연산과 Next.js 4단계 캐싱 아키텍처

📅 2026-07-03 · 섹션 6 Turbopack점진적 연산 4단계 캐싱use cache
⚡ 속도는 두 축으로 나뉜다. 개발 속도는 Turbopack — Rust 기반(기계어 컴파일·GC 없음·멀티스레딩)에 점진적 연산("한 번 계산한 건 다시 계산하지 않는다")으로 변경분만 갱신. 운영 속도는 4단계 캐싱 — 대전제는 "기본적으로 캐시하지 않는다"(Next 15), 필요할 때만 ① Request Memoization(한 렌더링 내 중복 fetch 제거) ② Data Cache(서버 창고, revalidate) ③ Full Route Cache(페이지 통째 굽기) ④ Router Cache(브라우저 메모리, 뒤로 가기 즉시 복원)를 연다. Next 16에선 'use cache' 한 줄로 이를 우아하게 제어 — "변화가 적고 무거운 연산에 붙인다".

1. 맥락 — 뼈대(24강) 위에 "속도"라는 날개

섹션 5에서 서버/클라 컴포넌트 구조(골격)를 잡았다. 이제 그 위에 성능을 얹는다. 속도는 두 개의 엔진이 책임진다.

🛠️ 개발 속도 — Turbopack

  • 코드 수정 → 화면 반영까지의 빌드 대기 시간을 없앤다

🚀 운영 속도 — 4단계 캐싱

  • 실제 사용자가 접속했을 때의 응답 속도를 결정한다

2. 번들링 — 왜 Webpack은 느려졌나

React 컴포넌트·JS·CSS·이미지는 그대로 브라우저에서 실행될 수 없다. 브라우저가 이해할 하나의 최적화된 결과물로 묶고 변환하는 작업이 번들링. 오랫동안 JavaScript 기반 Webpack이 맡았지만, 프로젝트가 거대해질수록 JS의 태생적 한계로 빌드 시간이 길어졌다.

3. 왜 Rust인가 — Turbopack이 빠른 근본 이유

🐢 JavaScript

  • 한 줄씩 읽으며 해석(인터프리트)하는 과정 필요
  • 가비지 컬렉터(청소부)가 주기적으로 개입 → 실행 흐름 정지

🦀 Rust

  • 하드웨어가 직접 이해하는 기계어로 미리 컴파일 (로우 레벨)
  • GC 없이 메모리를 안전·효율적으로 관리
  • 모든 CPU 코어를 동시 활용하는 멀티스레딩 최적화
🏭
JavaScript = 혼자서 일일이 서류를 번역·정리하는 직원 · Rust = 수십 명의 전문가가 기계로 동시에 서류를 찍어내는 공장.

4. 핵심 원리 — 점진적 연산 (Incremental Computation)

철학 한 줄: "한 번 계산한 것은 절대 다시 계산하지 않는다."

  • 함수 단위로 모든 작업 결과를 메모리에 캐시
  • 파일 간 의존성 지도를 완벽히 파악 → 변경 시 영향받는 부분만 정확히 찾아 갱신
🧱
거대한 레고 성에서 꼭대기 깃발 색 하나를 바꿨을 때 — 기존 번들러는 성벽 상당 부분을 허물고 재조립, Turbopack은 깃발과 그 깃발이 꽂힌 블록 하나만 업데이트.

사용법 — 허무할 정도로 간단

// package.json (Next.js 15)
"scripts": {
  "dev": "next dev --turbo"   // 플래그 하나로 끝
}

5. 캐싱 대전제 — "기본적으로 캐시하지 않는다"

캐싱 = 무겁게 가져온 데이터를 임시 창고에 저장해두고 다음 요청 때 바로 꺼내주는 기술. Next.js 15 캐싱의 출발점은 공식 문서의 대전제다.

📦 과거 버전

  • 데이터를 가져오면 프레임워크가 알아서 캐시
  • DB를 수정해도 화면이 안 바뀌는 대혼란

✅ Next.js 15

  • 개발자가 명시적으로 허락하지 않는 한 캐시 안 함
  • 항상 최신 데이터 — 안전한 기본값

6. 4단계 캐싱 아키텍처

계층위치수명·범위실무 대표 예
① Request Memoization서버 (React 기능)한 번의 렌더링 동안내비바·사이드바·본문이 각자 유저 정보 fetch
② Data Cache서버지속 (배포·revalidate까지)쇼핑몰 상품 목록·블로그 글 (1시간 캐시)
③ Full Route Cache서버빌드 산출물 (HTML+RSC Payload)회사 소개·이용약관·마케팅 랜딩
④ Router Cache브라우저 메모리세션 내 페이지 이동목록→상세→뒤로 가기 즉시 복원

① Request Memoization — 찰나의 기억 (React 고유 기능)

렌더링 시작~끝의 짧은 생명 주기 안에서 동일한 URL·옵션의 fetch가 여러 번 발생하면, 실제 네트워크 요청은 단 한 번. 나머지는 첫 응답을 재사용.

실무 효용 최상단 부모에서 불러와 props로 내려주는 복잡한 과정 없이, 데이터가 필요한 컴포넌트마다 독립적으로 fetch를 호출해도 성능 저하 걱정이 없다.

② Data Cache — 서버의 데이터 창고

// 기본은 캐시 OFF — 옵션으로 창고 문을 연다
fetch(url, { cache: 'force-cache' });          // 다음 배포까지 영구 저장
fetch(url, { next: { revalidate: 3600 } });   // 1시간마다 백그라운드 교체
비용 임팩트 1시간 캐시면 그동안 수십만 명이 접속해도 DB 쿼리는 단 한 번 → 서버 비용 대폭 절감. 사용자는 빠른 응답 + 비교적 최신 데이터.

③ Full Route Cache — 완성된 페이지를 통째로 굽기

데이터로 만든 HTML + RSC Payload(UI 결과물)를 서버에 통째로 저장. 정적 페이지는 전 세계 어디서든 CDN으로 즉시 제공 — 가장 빠른 캐싱 단계.

🍽️
주문마다 요리하는 게 아니라 잘 팔리는 메뉴를 미리 조리해두고 주문 즉시 내어주는 식당.

④ Router Cache — 유일한 클라이언트 캐시

앞의 셋은 서버, 이것만 브라우저 메모리. 사이트 내 이동 시 방문한 페이지 결과물을 임시 기억 → 뒤로 가기·재방문 시 서버 요청 없이 즉시 복원. 목록→상세→뒤로 가기에서 로딩 스피너 없이 스크롤 위치 그대로 나타나는 1등 공신.

7. Next.js 16 — 'use cache'로 우아하게 제어

과거엔 fetch 옵션에 복잡하게 설정을 넣었지만, 이제 함수/컴포넌트 최상단에 지시어 한 줄이면 결과를 Data Cache에 저장하고 Full Route Cache까지 최적 연동한다. 외부 API뿐 아니라 직접 연결한 DB 쿼리·무거운 데이터 가공 로직에도 적용.

🔥 원칙 한 줄 — 변화가 적고 무거운 연산에는 'use cache'를 붙인다.
⚠️ 섹션 5 팩트체크 연결 'use cache'는 Cache Components 기능으로 cacheComponents: true opt-in이 선행되어야 동작한다(24강 팩트체크에서 공식 문서 검증). "지시어 한 줄로 끝"은 설정 전제가 생략된 서술.
✅ 핵심 정리
· 개발 속도 = Turbopack (Rust: 기계어·GC 없음·멀티스레딩 + 점진적 연산)
· 운영 속도 = 4단계 캐싱, 대전제는 "기본 캐시 안 함" (Next 15)
· ① Memoization(한 렌더링) → ② Data Cache(서버 창고) → ③ Full Route(페이지 굽기) → ④ Router(브라우저)
· Next 16 제어법 = 'use cache' — 변화 적고 무거운 연산에
· 본질은 "중복 작업을 피하고, 미리 준비해 둔다"는 프로그래밍의 기본 진리
다음 강 예고 (26강) 최적화되어 빌드된 결과물이 실제로 얼마나 무거운지 — @next/bundle-analyzer로 번들 사이즈를 시각화하는 분석 기법.

26강. 코드의 무게를 재다

[번들 분석] 번들 분석기(experimental-analyze)를 활용한 100KB 마지노선 사수하기

📅 2026-07-03 · 섹션 6 번들 분석100KB 마지노선 TBT트리 쉐이킹
⚖️ 번들은 사용자가 전부 내려받아 파싱·컴파일·실행해야 하는 실제 무게다. 기준은 First Load JS 100KB 미만(100~200KB 황색, 200KB+ 적색) — 압축 170KB ≈ 해제 1MB ≈ 중저사양 폰에서 메인 스레드 1~2초 블로킹(TBT)이기 때문. Next 16.1+ Turbopack에선 설치 없이 npx next experimental-analyze 한 줄로 트리맵 시각화(과거 ANALYZE=true는 Webpack용이라 무효). 다이어트 처방 3가지: ① optimizePackageImports(거대 패키지 트리 쉐이킹) ② 무거운 렌더링은 서버 컴포넌트로(prism→shiki, moment→date-fns) ③ serverExternalPackages(서버 전용 모듈 번들링 제외).

1. 맥락 — 엔진(25강)을 달았으니 이제 "무게"를 잰다

Turbopack·캐싱으로 개발/서버 속도를 잡았다면, 이번엔 사용자에게 전달되는 실제 무게를 과학적으로 점검할 차례. 번들 = 우리가 쓴 JS + 외부 라이브러리가 빌드를 거쳐 브라우저가 읽기 좋게 합쳐진 결과물.

왜 무게가 생존 문제인가 브라우저 V8 엔진은 코드를 다운로드한 뒤 파싱 → 컴파일 → 실행이라는 무거운 연산을 거친다. 파일이 무거우면 해석·실행 시간도 정비례로 늘고, 특히 저사양 모바일에선 번들 사이즈가 곧 이탈률(Bounce Rate)로 직결된다.

2. 기준 정립 — 100KB 마지노선과 TBT

First Load JS (페이지당)신호행동
< 100KB🟢 녹색매우 훌륭 — 유지
100 ~ 200KB🟡 황색최적화 고민 시작
> 200KB🔴 적색반드시 무거운 로직 제거

이 기준의 뿌리는 Lighthouse·Core Web Vitals 권고. 수치의 근거:

  • 압축 JS 170KB ≈ 압축 해제 시 약 1MB
  • 중저사양 폰에서 1MB를 읽고 실행하는 데 1~2초 — 이 동안 메인 스레드가 꽉 막힘
  • 이 지연이 TBT(Total Blocking Time, 총 차단 시간) — 브라우저 메인 스레드는 싱글 스레드라 JS 실행 중엔 버튼을 눌러도 무반응·애니메이션 정지(렌더링 블로킹)
→ 100KB는 단순 용량이 아니라 사용자가 느끼는 상호작용의 쾌적함을 지키는 마지노선.

3. 엑스레이 장비 — npx next experimental-analyze

Next.js 16.1+ & Turbopack 환경이면 패키지 설치조차 불필요. 명령어 하나로 브라우저에 대화형 UI가 열린다.

# 대화형 분석 (트리맵 UI)
npx next experimental-analyze

# 정적 리포트로 저장 → 최적화 전후 비교용
npx next experimental-analyze --output   # .next/diagnostics/analyze 에 저장
cp -r .next/diagnostics/analyze ./analyze-before-refactor   # 통째로 백업
  • 트리맵 시각화 — 모듈 크기를 사각형 면적으로 표시 (클수록 비중 큼)
  • 필터·검색 — 라우트 경로 / 클라이언트·서버 환경 / JS·CSS 파일 타입별, 파일명 검색
  • 임포트 체인 추적 — 사각형 클릭 시 정확한 용량 + 어디서 이 모듈을 쓰는지 끝까지 추적

왜 ANALYZE=true npm run build는 안 되나

📦 과거 — Webpack 시절

  • ANALYZE=true는 @next/bundle-analyzer 플러그인을 깨우는 신호탄
  • 패키지 별도 설치 + 전체 빌드 필요 (느림)
  • 정적 HTML 탭 3개가 열리는 방식

⚡ 현재 — Turbopack (Next 16.1+)

  • Rust 기반 Turbopack은 구형 신호탄을 못 알아듣고, Webpack 전용 플러그인과 기술적 충돌(리포트 생성 무시)
  • 설치·설정 없이 명령어 하나
  • 분석용 스캔만 수행해 빠름 + 대화형 UI

4. 무거운 번들 다이어트 — 3가지 처방

① 거대 패키지 → optimizePackageImports (트리 쉐이킹)

아이콘·유틸리티처럼 수백 개 모듈을 내보내는 거대 패키지는 편하게 통째로 import해도, 빌드 시점에 실제 사용한 모듈만 골라 로드하게 만든다.

// next.config.mjs
const nextConfig = {
  experimental: {
    optimizePackageImports: ['lucide-react', 'lodash'],
  },
};
트리 쉐이킹(Tree-shaking) 나무를 흔들어 죽은 잎을 떨어뜨리듯, 컴파일러가 AST(추상 구문 트리)를 분석해 안 쓰는 코드를 빌드 결과물에서 도려내는 기법. Next.js가 인기 라이브러리 다수는 이미 자동 최적화하므로, 자동 지원 목록에 없는 거대 패키지에만 명시하면 된다.

② 무거운 렌더링 → 서버 컴포넌트로 이동

구문 강조·차트·마크다운 파싱처럼 데이터를 UI로 변환만 하는 라이브러리가 클라이언트에 있으면, 결과물은 단순 HTML인데 방대한 파싱 라이브러리를 통째로 다운로드·실행하게 된다.

🔥 판별 기준 — 브라우저 전용 API나 사용자 상호작용이 필요 없다면 → 서버 컴포넌트로 옮기는 게 정답.

❌ 최적화 전 (클라이언트)

'use client'
import moment from 'moment';
import Highlight from
  'prism-react-renderer';
// 전부 브라우저로 전송 → 번들 폭발
  • moment: OOP 구조로 전 세계 언어팩이 한 덩어리 → 트리 쉐이킹 불가, 함수 하나 써도 통째로 끌려옴
  • prism: 사용자 기기 CPU로 실시간 파싱·토큰화

✅ 최적화 후 (서버)

// 'use client' 제거 → RSC
import { format } from 'date-fns';
import { codeToHtml } from 'shiki';

const html = await codeToHtml(code, {...});
// 클라엔 완성된 마크업만 전달
  • date-fns: 순수 함수 기반 → 완벽한 트리 쉐이킹
  • shiki: 서버에서만 실행 → 클라 번들 0KB
  • dangerouslySetInnerHTML로 완성 HTML 주입 → 제로 JS 렌더링

③ 서버 전용 패키지 → serverExternalPackages (번들링 제외)

Next.js는 서버 컴포넌트·라우트 핸들러에서 import한 패키지도 자동 번들링한다. Node 내장 모듈(os·fs)이나 네이티브(C++) 모듈처럼 번들에 묶이면 안 되는 것들은 외부 모듈로 남겨둔다.

// next.config.mjs
const nextConfig = {
  serverExternalPackages: ['os'],  // "건드리지 말고 서버 원본 그대로 실행"
};

5. 핸즈온 결과 — 전후 비교

  • Before: moment가 트리맵을 꽉 채운 거대 사각형 + prism-react-renderer도 상당 → First Load JS 100KB 훌쩍 초과
  • After: moment 박스 소멸 → 작은 date-fns 조각만, shiki는 클라이언트 맵에 아예 없음(0KB) → First Load JS 100KB 미만 진입
⚖️
번들 사이즈 관리는 다이어트다 — 한 번 뺀다고 끝이 아니라, 새 라이브러리를 추가할 때마다 분석기라는 체중계에 올라 정기적으로 재며 가볍게 유지해야 한다.
✅ 핵심 정리
· 기준: First Load JS 100KB 미만 (근거 = 압축 170KB ≈ 1MB ≈ 메인 스레드 1~2초 블록 = TBT)
· 측정: npx next experimental-analyze (Next 16.1+ Turbopack 내장 · ANALYZE=true는 Webpack 유물)
· 처방 ①: optimizePackageImports — 거대 패키지 트리 쉐이킹
· 처방 ②: 변환만 하는 무거운 렌더링은 서버 컴포넌트로 (moment→date-fns · prism→shiki)
· 처방 ③: serverExternalPackages — 서버 전용 모듈은 번들링 제외
· 관리: 라이브러리 추가 때마다 정기 측정 (다이어트)
다음 강 예고 (27강) 상호작용이 일어나는 시점까지 스크립트 로딩을 정교하게 미루는 핵심 기술 — 다이나믹 임포트(Dynamic Import).

27강. 필요한 순간에만 소환하기

[지연 로딩] next/dynamic 동적 임포트와 CLS를 방지하는 스켈레톤 전략

📅 2026-07-05 · 섹션 6 next/dynamic청크 분리 CLS 방어프리로드
🗡️ 26강이 진단(분석기)이었다면 27강은 수술칼 — 무거운 컴포넌트를 초기 번들에서 도려내 필요한 순간에만 청크로 소환한다. 도구는 next/dynamic(= React.lazy+Suspense 복합체, Pages/App 라우터 공용). 실무 3대 포인트: ① loading 스켈레톤으로 CLS 방어 ② ssr: false로 window 의존 라이브러리의 서버 렌더 에러 차단 ③ 조건부 로딩 + onMouseEnter 프리로드로 클릭 시 지연 0. 단, 서버 컴포넌트는 이미 자동 스플리팅이라 대상이 아니다 — 'use client' + 무거운 서드파티일 때만 칼을 꺼낸다.

1. 맥락 — 진단(26강) 다음은 수술

분석기로 확인한 "거대한 돌덩이"(에디터·차트 등 500KB~1MB급)를 정적 import하면, 대시보드만 보러 온 사용자도 보이지도 않는 에디터 코드를 통째로 다운로드·파싱해야 한다 — 자원 낭비이자 이탈률 직격탄.

청크(Chunk)란 빌드 도구(Webpack/Turbopack)가 코드를 "첫 화면에 당장 필요한 메인 덩어리"와 "나중에 불러도 되는 서브 덩어리들"로 물리적으로 분리한 파일 조각. 동적 임포트는 특정 시점에 그 청크 파일만 쏙 네트워크로 가져오는 기술이다.

지연 로딩 구현법은 공식적으로 둘: next/dynamic(오늘의 주인공)과 React.lazy+Suspense 직접 사용. next/dynamic은 둘을 결합한 복합체로, Pages·App 라우터 양쪽에서 동일 동작 → 점진적 마이그레이션에도 유용.

2. 실무 3대 포인트

const HeavyEditor = dynamic(() => import('@/components/HeavyStudyLogEditor'), {
  loading: () => <EditorSkeleton />,  // ① CLS 방어
  ssr: false,                         // ② window 의존 → 서버 렌더 스킵
});
const AdvancedChart = dynamic(() => import('@/components/AdvancedChart'));
...
<button
  onMouseEnter={() => import('@/components/AdvancedChart')}  // ③ 프리로드
  onClick={() => setShowChart(!showChart)}
>
{showChart && <AdvancedChart />}  // ③ 조건부 — 클릭 순간에만 청크 다운로드
  • ① loading 스켈레톤 — CLS 방어: 청크 다운로드 지연 동안 화면이 비었다가 에디터가 튀어나오면 레이아웃이 밀린다 = CLS(누적 레이아웃 이동), SEO 큰 감점. 실제 컴포넌트와 동일한 크기의 스켈레톤을 넣어 방어.
  • ② ssr: false: React.lazy/Suspense는 클라 컴포넌트도 기본적으로 서버에서 사전 렌더링을 시도 → window를 만지는 에디터·차트는 런타임 에러. 이 옵션으로 "클라이언트에서만 로드" 지시. 클라이언트 컴포넌트 안에서만 동작.
  • ③ 조건부 로딩 + 프리로드: 상태가 true 되는 순간 온디맨드 로드하되, 클릭 후 다운로드 딜레이가 남는다 → onMouseEnter에서 import()를 미리 호출해 클릭 직전 찰나에 백그라운드 다운로드 → 클릭 시 지연 0.

3. 고급 문법 2가지

📦 Named export 가져오기

const ClientHello = dynamic(() =>
  import('../components/hello')
    .then((mod) => mod.Hello)
);

export const Hello 형태는 Promise의 .then으로 모듈에서 꺼내 연결.

🔧 순수 JS 라이브러리

onChange={async (e) => {
  const Fuse =
    (await import('fuse.js')).default;
  const fuse = new Fuse(names);
}}

타이핑 시작 순간에만 검색 엔진 로드. 검색 안 하면 평생 다운로드 안 됨. .default 필수.

4. 서버 컴포넌트와의 관계 — "전부 dynamic으로?"는 오답

⚠️ RSC 예외 상황

  • 서버 컴포넌트는 애초에 대상이 아니다 — 프레임워크가 자동 코드 스플리팅 + 스트리밍을 적용하고 클라 번들에 포함되지도 않는다. 지연 로딩의 타겟은 클라이언트 컴포넌트.
  • 서버 컴포넌트 안에서 클라 컴포넌트를 dynamic → 강의는 "정상 스플리팅"이라 했으나 공식 문서는 "currently not supported"로 정반대 — 팩트체크 카드 1번 참조 ⚠️
  • 서버 컴포넌트 자체를 dynamic → 그 컴포넌트가 아니라 자식 클라 컴포넌트들만 지연 로딩됨 (CSS 등 정적 자산 프리로드 정도의 의미)
  • ssr: false를 서버 컴포넌트에서 쓰면 에러 — 반드시 클라 컴포넌트 내부로
🔥 판단 기준 — 'use client' 컴포넌트이면서 무거운 서드파티를 품고 있을 때만 next/dynamic의 칼을 꺼낸다.

5. 트러블슈팅 — 수정했는데 분석기 결과가 그대로일 때

  • ① 정적 import 잔존 (최다 빈도) — 상단에 기존 import Heavy...가 한 줄이라도 남아 있으면 빌드 도구는 스플리팅을 포기하고 메인 번들에 합침
  • ② .next 캐시 — rm -rf .next 후 재빌드
  • ③ 임포트 누수 — 다른 파일(layout·공통 컴포넌트)이 같은 라이브러리를 정적 import 중이면 도로 아미타불. 전역 검색으로 누수 지점 색출
🔗 우리 프로젝트 연결 이 강의 내용은 섹터 3에서 이미 실전으로 검증했다 — lessee/lessor의 next/dynamic 142건, heic2any의 await import()(모범 사례), Lottie JSON의 "팝업 오픈 시" 조건부 로드, QATools dynamic 전환. 특히 트러블슈팅 ①·③은 우리의 Lottie(배럴 정적 export가 누수 지점)·QATools(정적 import 잔존) 사례와 정확히 같은 패턴.
✅ 핵심 정리
· next/dynamic = React.lazy + Suspense 복합체 (Pages/App 공용)
· ① loading 스켈레톤(CLS 방어) ② ssr:false(window 의존) ③ 조건부 + onMouseEnter 프리로드
· named export는 .then(mod => mod.X) · 순수 JS는 (await import()).default
· 서버 컴포넌트는 자동 스플리팅 — 타겟은 'use client' + 무거운 서드파티
· 안 줄면: 정적 import 잔존 · .next 캐시 · 임포트 누수 순으로 의심
다음 강 예고 (28강) 화면 성능 최적화의 꽃 — next/image와 WebP·AVIF를 활용한 미디어 최적화. 가장 용량이 큰 이미지를 똑똑하게 서빙하는 법.

28강. 웹 이미지의 종착역

[미디어 최적화] next/image와 차세대 포맷 AVIF로 구현하는 시각적 안정성

📅 2026-07-05 · 섹션 6 next/imageAVIF fill + sizespriority
🖼️ 웹 트래픽 최대 항목은 이미지 — 날것의 <img>는 손톱만한 프로필 칸에 5MB 원본을 통째로 내려받는 직무유기다. next/image의 4대 최적화: ① 기기별 사이즈 + 최신 포맷 자동 변환 ② 공간 선확보로 CLS 자동 방지 ③ 네이티브 지연 로딩 ④ 원격 이미지 온디맨드 리사이징. 포맷은 JPEG(레거시) → WebP(과도기, -25~35%) → AVIF(실무 표준, WebP보다 +20% 압축·JPEG 대비 절반 이하·HDR). 실무 4종 세트: remotePatterns 핀셋 보안 · fill+sizes(생략 시 100vw 낭비) · placeholder="blur" · LCP 이미지엔 priority. 트래픽이 커지면 최적화를 외부 이미지 CDN에 위임이 다음 스텝.

1. 맥락 — <img> 날것 사용은 직무유기

4K·5MB JPEG를 모바일의 손톱만한 프로필 칸에 띄우려고 5MB 전부를 다운로드하는 것이 일반 <img>의 현실 — 데이터 낭비 + 버벅임의 원인. next/image는 <img>를 내부 확장해 4가지를 자동화한다:

  • ① 사이즈 최적화 — 기기에 맞는 정확한 크기 + WebP/AVIF 자동 변환 서빙
  • ② 시각적 안정성 — 이미지가 차지할 공간을 미리 확보해 로딩 지연에도 레이아웃 밀림(CLS) 차단
  • ③ 빠른 페이지 로드 — 브라우저 네이티브 지연 로딩
  • ④ 자산 유연성 — 원격 서버 이미지까지 온디맨드 리사이징

2. 포맷 발전사 — JPEG → WebP → AVIF

포맷위상특징
JPEG / PNG레거시 표준압축 효율 낮음 — 고해상도일수록 용량 기하급수 증가
WebP (구글)과도기 표준JPEG 대비 -25~35% + 투명도·애니메이션 지원. 구형 브라우저용 폴백
AVIF (넷플릭스·구글 주도)실무 표준WebP보다 압축률 +20%, JPEG 대비 화질 손상 없이 용량 절반 이하, HDR 표현력 우수

3. 로컬 이미지 — 정적 임포트가 정답

📁 public 경로 방식

<Image src="/profile.png"
  width={500} height={500} />
// 수동으로 너비·높이 명시 필요

✅ 정적 임포트 (강력)

import ProfileImage from './profile.png';
<Image src={ProfileImage}
  placeholder="blur" />
// 빌드 시 width·height·blurDataURL 자동
왜 강력한가 빌드 시점에 원본 픽셀을 분석해 크기를 자동 할당 → 사이즈를 안 적어도 CLS 방지. 블러 썸네일(blurDataURL)까지 자동 생성.

4. 원격 이미지 — 보안 설정이 선행 조건

S3 같은 원격 이미지는 빌드 시점에 크기를 알 수 없다 → 수동 width/height(+blurDataURL) 또는 fill. 그리고 최적화 API 악용(해커가 8K 이미지를 우리 서버로 압축시켜 CPU·과금 폭탄)을 막기 위해 허용 목록이 필수:

// next.config.mjs
images: {
  formats: ['image/avif', 'image/webp'],  // 배열 "순서"가 핵심 — Accept 헤더 보고 앞에서부터 분기
  remotePatterns: [{
    protocol: 'https',                       // 암호화 통신만
    hostname: 'study-planner.s3.…amazonaws.com', // 정확한 버킷만
    pathname: '/uploads/**',                 // 특정 폴더 하위만
    search: '',                              // 쿼리까지 통제
  }],
}
formats 분기 AVIF 지원 브라우저 → AVIF, 아니면 WebP, 둘 다 모르면 원본(JPEG/PNG) — 한 줄로 자동 처리. remotePatterns는 구식 domains를 대체하는 핀셋 보안.

5. fill + sizes — 반응형 원격 이미지의 핵심 콤보

<article className="relative w-full h-64 …">  // 부모에 relative/absolute 필수!
  <Image
    src={imageUrl} alt={altText}
    fill                                      // 부모 크기에 꽉 차게
    sizes="(max-width: 768px) 100vw, (max-width: 1200px) 50vw, 33vw"
    className="object-cover"                // 비율 안 맞을 때 크롭
    priority                                  // LCP 이미지면 최우선 다운로드
    placeholder="blur" blurDataURL="data:image/png;base64,…"  // 원격은 수동
  />
</article>
  • sizes 생략 = 100vw 기본값 — 3열 그리드의 작은 카드에도 화면 전체 너비 기준 거대 이미지를 받는 대역폭 낭비. "모바일 100vw·태블릿 50vw·데스크탑 33vw"처럼 브라우저에 지시해야 실무 최적화
  • priority — 상단 배너처럼 LCP에 영향 주는 이미지는 기본 지연 로딩이 오히려 감점 → 최우선 다운로드 지시
  • 원격의 blur — 정적 임포트와 달리 자동 생성이 없으므로 blurDataURL에 초소형 Base64를 수동 주입

6. 실무 주의 — 서버가 깎는 비용

대규모 트래픽의 함정 Next.js 서버가 직접 AVIF로 압축하는 건 CPU를 꽤 소모한다. 하루 수십만 장 업로드 규모라면 Cloudinary·imgix·CloudFront 등 전문 이미지 CDN에 최적화를 위임하는 것이 다음 스텝.

7. 트러블슈팅 3종

  • "Unconfigured Host" 에러(엑스박스) — 100% remotePatterns 미등록. 의도된 보안 차단이니 도메인 추가
  • 이미지가 화면을 덮거나 사라짐 — fill의 부모에 포지션(relative 등)·명시적 높이가 없어서. fill은 "부모 울타리" 기준으로 뻗는다
  • 콘솔의 LCP priority 경고(노란 글씨) — 상단 큰 이미지에 지연 로딩이 걸려 있다는 신호. priority 반영으로 성능 점수 사수

1. 결정적 오류 — "서버 → 클라 dynamic은 정상 스플리팅" ✗

강의는 RSC 예외 상황 첫째로 "서버 컴포넌트 내부에서 클라이언트 컴포넌트를 next/dynamic으로 가져올 경우 해당 클라이언트 컴포넌트와 그 종속성들은 정상적으로 코드 스플리팅이 이루어집니다"라고 단정한다. 공식 문서의 현행 서술은 정반대다:

📄 문서 원문 (v16.2.10)

"When a Server Component dynamically imports a Client Component, automatic code splitting is currently not supported."

  • 즉 서버 컴포넌트에서 dynamic()으로 클라 컴포넌트를 불러도 지연 로딩 효과가 없다(정적 import처럼 번들에 포함) — 현재 알려진 제약.
  • 실무 귀결: 스플리팅이 목적이라면 dynamic 호출을 클라이언트 컴포넌트 내부로 옮겨야 한다. ssr:false를 클라로 옮기라는 문서 노트("move it into Client Components ensure the client code-splitting working properly")도 같은 맥락.
  • 과거 문서엔 "동작한다"고 쓰여 있던 시기가 있어 강의가 낡은 서술을 참조했을 가능성 — 버전 명시 없는 단정의 위험 사례.

2. CLS "SEO 큰 감점" — 과장

CLS 정의(레이아웃 밀림)와 스켈레톤 처방은 정확하다. 다만 CLS는 Core Web Vitals의 하나로 랭킹 신호에 포함되지만, 구글 공식 입장은 "콘텐츠 관련성이 우선이고 CWV는 여러 신호 중 하나"다. "큰 감점"보다 정확한 프레임: CLS의 진짜 비용은 UX(누르려던 버튼이 밀려 오조작·이탈)이고 SEO는 부차 효과.

3. onMouseEnter 프리로드 — 기법은 진짜, 우리 환경엔 번역 필요

  • 원리 검증: import()는 모듈 캐시를 공유하므로 프리로드로 한 번, 렌더에서 또 한 번 호출해도 중복 다운로드 없음 — 안전한 패턴.
  • ⚠️ 맥락: 자리톡처럼 모바일 웹뷰 중심 서비스엔 hover 이벤트가 없다. 같은 목적의 번역판: 뷰포트 진입 시 프리로드(IntersectionObserver), onTouchStart(클릭 확정 ~수십ms 전), 또는 라우트 프리페치. 데스크톱 전용 기법을 그대로 쓰면 무의미.

4. 도구 서술 혼용 — 26강 회고와 실습 가이드

  • 26강 회고 불일치 — "26강에서 @next/bundle-analyzer라는 X-ray 장비로 시각화했다"고 회고하지만, 26강의 장비는 experimental-analyze였고 bundle-analyzer는 그 강의 스스로 "구형 신호탄"이라 했다.
  • "반드시 npm run build 후 분석기 실행" — experimental-analyze는 자체 스캔을 수행하므로 사전 빌드가 필요 없다(문서: "Does not produce build artifacts" · 우리 실측: 빌드 없이 단독 25~39초 동작). 빌드 산출물을 읽던 구세대(webpack-bundle-analyzer) 워크플로의 잔재.
  • "First Load JS 용량 표기"·"Parsed Size" — First Load JS는 Next 16에서 제거된 빌드 출력 지표명이고, Parsed Size는 webpack-bundle-analyzer의 UI 용어. 새 분석기(트리맵·임포트 체인) 서술에 구세대 UI 용어가 섞여 있다.
